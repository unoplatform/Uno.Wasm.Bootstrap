# Feature Specification: AOT Wrapper Seeding for Profile-Guided AOT

**Feature Branch**: `dev/mikernet/aot-wrapper-seeding`
**Created**: 2026-10-27
**Status**: Implemented
**Input**: Bug fix for profile-guided AOT builds that abort at run time with an `interp.c` assertion when compiled code calls through an interface.

## Overview

With an AOT profile, the Mono AOT compiler runs in `profile-only` mode: it compiles the methods the profile lists and leaves the rest to the interpreter. In `llvmonly` mode, which browser-wasm uses, compiled code enters the interpreter through interpreter entry wrappers that must be compiled ahead of time: a `gsharedvt_in_sig` wrapper for up to 8 parameters, an `interp_in` wrapper above that. The compiler only emits the wrappers for signatures that compiled call sites use.

The first call through an interface builds the class's IMT slot for that method, and the runtime then resolves every interface method that hashes to the same slot (19 slots per class). For a sibling method that isn't compiled, the runtime needs its wrapper. A missing `gsharedvt_in_sig` wrapper is replaced by a stub that only fails if it's called, but a missing `interp_in` wrapper makes the runtime abort:

```text
[MONO] * Assertion at .../src/mono/mono/mini/interp/interp.c:3420, condition `<disabled>' not met
```

Interface methods that didn't run while the profile was recorded, or were added or renamed since, are interpreted, so such a method with more than 8 parameters can break calls to other, compiled methods of the classes that implement its interface. This specification makes the bootstrapper prevent the abort by making the AOT compiler emit the wrappers. The user documentation (`doc/runtime-execution-modes.md`, "Preventing crashes in profile-guided AOT builds") describes it without the internals below.

## Design

- Before the AOT compilation, `GenerateAOTWrapperSeedsTask_v0` reads the AOT inputs with Mono.Cecil and collects the signatures of the methods the runtime may enter the interpreter for without a compiled call site that names their signature (FR-2).
- It writes a seed assembly, `Uno.Wasm.AotWrapperSeeds`, and an AOT profile that lists only its seed methods. Each seed method calls target methods of the collected signatures directly, and the targets aren't compiled. A direct call from compiled code into a method of the same assembly that the profile doesn't list may enter the interpreter, so the AOT compiler records the callee's signature (`can_enter_interp` and `mini_emit_method_call_full` in `calls.c`) and emits its interpreter entry wrapper (`compile_method` in `aot-compiler.c`). The calls are on the fall-through path of a branch that is always taken (`ldc.i4.0`, `brfalse`), so they never run: `mono_method_to_ir` in `method-to-ir.c` converts every block that a branch can reach (it only skips the blocks that `mono_basic_block_split` in `mono-basic-block.c` finds unreachable), which records the signatures, and the calls are then removed as dead code, so the seed methods compile to almost no code. After an unconditional branch, the calls would be unreachable, and skipped with their signatures. The AOT compiler merges the profiles it's given, so the application's own profile still decides which of its methods are compiled.
- Nothing references the seed assembly and it isn't published: only its compiled seed methods and the wrappers end up in `dotnet.native.wasm`. With AOT deduplication (`WasmDedup`, on by default), the wrappers go to the `aot-instances` module, where the runtime looks for dedupable methods such as these wrappers (`find_aot_method` and `mono_aot_can_dedup` in `aot-runtime.c`). Without it, they would only be in the seed assembly's own module, which the runtime never loads, hence the requirement in FR-1.
- After the AOT compilation, `ValidateAOTWrapperSeedsTask_v0` lists the functions that `aot-instances.dll.bc` defines with `llvm-nm --defined-only` and looks for the expected wrapper names (FR-4, FR-5). The names come from a reimplementation of the runtime's signature normalization and naming (`WrapperSignature`), which works on the UTF-8 bytes of type names as the runtime does, with `char` signed except on Linux Arm and Arm64 build machines (32-bit and 64-bit); lays value types out as `mono_class_layout_fields` in `class-init.c` does (a packing raises the alignment up to that of a double, fields with references keep the pointer alignment, and an explicit size isn't rounded up); sizes inline arrays by their length; keeps function pointers as they are, described as `*()`; and re-inflates generic value types with the shared types of their arguments before it maps their fields, as `get_wrapper_shared_type_full` in `mini-generic-sharing.c` does. Name prediction only verifies the build: a seed whose names can't be predicted is seeded anyway and listed as unchecked. The extended layouts of .NET 11 (`[ExtendedLayout]` C structs and unions) keep their own type, like explicit ones, as `get_wrapper_shared_vtype` only maps auto and sequential layouts. Seeds with a value type whose layout is cyclic are left out instead (FR-2).
- The files are written to `obj/<configuration>/<target framework>/aot-wrapper-seeding`: the seed assembly, its profile (`Uno.Wasm.AotWrapperSeeds.profile`), `Uno.Wasm.AotWrapperSeeds.wrappers.txt`, which lists each expected wrapper with a method that needs it, and a stamp named after the bootstrapper's version, `generated.v0.stamp` in the sources (see "Republishing"). `dotnet clean` removes the folder.
- Cost, measured on .NET 10.0.12. In the test app (from an empty `obj` both ways), `dotnet.native.wasm` grows from 3,299,984 to 3,322,858 bytes (+22 KB, +0.69%; +3.7 to 5.2 KB, +0.30 to 0.43%, with gzip at level 9, depending on its implementation; Brotli varies by several KB at this size) for 259 seeds, with 153 `gsharedvt_in_sig` and 8 `interp_in` wrappers expected; its seed module links to about 1.5 KB. In a large app (131 AOT-compiled assemblies, a 36.4 MB `dotnet.native.wasm`, 7.5 MB with Brotli), the seeding expects 1,760 `gsharedvt_in_sig` and 2 `interp_in` wrappers for 3,966 seeds. 941 of them aren't in the build without it, and the seeding adds 955 wrappers in all, with those the AOT compiler makes alongside. That app is too large to link on the measuring machine, so its seeds were AOT-compiled like the SDK does and linked into the test app under the SDK's pipeline: the seed module links to 21.6 KB, and the new wrappers take about 74 KB of code and 70 to 78 KB of data, about 166 to 173 KB in all, 0.46 to 0.48% of `dotnet.native.wasm` (about 0.37% with gzip and 0.35% with Brotli). When the seed methods made their calls, the seed module alone took 255 KB. The seed module never runs. Generating the seeds takes about 3 to 10 seconds in that app, depending on the machine's load (peak working set about 490 to 530 MB, 1.8 GB allocated), and the check under a second, in a publish of several minutes.

## Functional Requirements

**FR-1**: When `WasmShellEnableAOTWrapperSeeding` is `true` (the default), `RunAOTCompilation` is `true`, the SDK AOT-compiles the build with the Mono runtime (`UseMonoRuntime` isn't `false`), `WasmAotProfilePath` is set, and AOT deduplication is on (`WasmDedup` is `true`, the default), the `_UnoGenerateAOTWrapperSeeds` target SHALL run `GenerateAOTWrapperSeedsTask_v0` before `_WasmAotCompileApp`, unless the files of an earlier run are up to date (FR-9). When deduplication is off, it SHALL log the `UNOWASM009` warning instead and skip the seeding and the check: without deduplication, the wrappers would only be in the seed assembly's AOT module, which the runtime never loads.

**FR-2**: The task SHALL collect, from the assemblies about to be AOT-compiled:

- the virtual instance methods of every interface each type implements (directly, through base types or through other interfaces), of every interface definition, and of every interface instance the code names, such as the one of a call site (`build_imt_slots` in `object.c` only puts virtual instance methods in IMT slots; the class that implements an interface can be created where the task can't see it);
- the methods loaded by `ldftn` and `ldvirtftn`;
- the instances of generic virtual methods that the code calls: they aren't in IMT slots (`build_imt_slots` skips generic methods), but code compiled once for any value type argument calls them with the generic parameters too, for the reason below;
- the virtual methods declared with the generic parameters of their type, of generic instances and of their generic base types. The runtime only initializes a virtual method table slot when compiled code calls it (`mini_llvmonly_init_vtable_slot` in `llvmonly-runtime.c`), and the AOT compiler emits the wrapper of the signature the call site names, which is the override's. Code compiled once for any value type argument (`gsharedvt`), which profile-guided builds have, names signatures with the generic parameters instead of the value types, so no call site names the signature of, for example, the `Compare (T, T)` override of a `Comparer<MyStruct>`. Delegate types are left out: the runtime enters the interpreter through their targets, not through `Invoke`, `BeginInvoke` or `EndInvoke`.

The generic instances SHALL be collected as follows:

- **Followed instances.** The types SHALL include the closed generic instances that the code and the collected signatures name, and those that the code of generic methods and of generic instances constructs, read from their bodies with their generic arguments: the generic methods and methods of generic types that closed code calls, and the methods of generic instances that the runtime reaches without a call that names the instance. Those are the virtual methods (overrides, interface and default implementations, the `MoveNext` methods of the state machines of async methods and iterators), which it reaches through virtual method tables and IMT slots; the static constructors (static field initializers), which it runs when it initializes the type; the parameterless constructors (instance field initializers included), which `new T()` runs through `Activator.CreateInstance<T>`, as `new Lazy<T>()` does; and the static methods that implement static abstract interface members, which constrained calls reach through the interface method. The implementations of generic virtual methods, of generic interface methods and of generic static abstract members, in classes and structs that aren't generic nor nested in generic ones, SHALL be followed too: a call names the method they override or implement, and the runtime picks the implementation, so each is followed with the generic arguments of every call, or delegate, to a generic virtual method of its name, number of generic parameters and number of parameters, which over-approximates the pairs. In generic classes and structs, each instance would pair with every call: in a large app, that multiplied the instances of LINQ's iterators until the bounds stopped them, so those aren't followed (see "Non-Goals"). This SHALL apply over value and reference types alike: the runtime enters the interpreter for the methods of an instance over reference types with the signatures of the instance, even though their code is shared. Instances of generic code that has no operands that depend on its generic parameters and no parameter of a generic parameter's type with flags (FR-8) are left out, as following them finds nothing.
- **What's skipped.** Instances, and arguments of generic code, that nest generic instances more than 8 deep SHALL be skipped: this bounds the expansion of code and signatures that name ever deeper instances, such as a method of `C<T>` that returns `C<ValueTuple<T>>` (the AOT compiler stops at the same depth, `check_type_depth` in `aot-compiler.c`). Signatures with generic parameters, `TypedReference`, `ArgIterator`, `RuntimeArgumentHandle`, or types that don't resolve among the AOT inputs SHALL be skipped. Signatures with a value type whose layout is cyclic SHALL be left out, and the structs at the root of the cycles reported with `UNOWASM010` (FR-8). The root of a cycle is the struct that holds the next type of the cycle in a field, the first in the order of their identities when several do, so that the types of one cycle (`Node`, `ReadOnlyMemory<Node>`) and the structs that hold them (`Memory<Node>`, `Span<Node>`) give the same root; a generic struct is reported by its definition, for all its instances. The task SHALL find the root of each type once per generation, and SHALL keep the shapes and sizes of the value types it walks, with the depth and steps of their walks, so that the walk bounds give what walking again would give. A struct that holds a struct over itself, such as `struct Node { ReadOnlyMemory<Node> Children; }`, which C# and the runtime accept, makes `get_wrapper_shared_type_full` map its type arguments and fields without end (it maps the type arguments of a generic struct first, then each field, with no guard), so the AOT compiler would overflow its stack on such a seed, which fails the whole build; the runtime does the same when it needs such a wrapper, whatever the seeding does. A struct that holds itself through its fields, in any layout, is invalid metadata, which C# rejects (CS0523) but IL writers can emit. Signatures with a generic struct of 16 type arguments or more, which C# and the runtime accept, SHALL be left out the same way, whether the signature has the struct itself, a struct that holds it in a field, or a generic struct over it, and the struct reported by its definition: `get_wrapper_shared_type_full` asserts `inst->type_argc < 16` before it maps the type arguments of a generic struct (its `args` array holds 16), so the AOT compiler would abort on such a seed, which fails a publish that succeeds without the seeding (measured with .NET 10.0.13: an interface method that only interpreted code calls, taking such a struct by value, makes the AOT compiler abort at `mini-generic-sharing.c:1402` with the seeding, and not without it); the runtime aborts the same way when it needs such a wrapper, whatever the seeding does. Classes, arrays and pointers over such a struct, and references to it, aren't affected: the runtime maps them to `object` or `intptr&` without mapping the struct.
- **Identity and merging.** Types SHALL be told apart by the assembly that defines them as well as by name: same-named types of different assemblies are different types to the runtime, with wrappers of their own. Signatures that the runtime passes alike SHALL be merged: `bool` with `byte`, `char` with `ushort`, enums with their underlying types, references with each other, and generic value types that only differ in reference type arguments (`get_wrapper_shared_type_full` re-inflates them with `object`). Instances of generic types and methods that only differ in reference type arguments have the same normalized signatures, so one of them SHALL stand for all.
- **Bounds.** Recursive generic code can make ever larger or ever more instances, so the task SHALL follow no instance whose generic arguments hold more than 64 named types, counting each reference type argument as one, as the runtime shares them (more than three times the 18 of a large app's largest), at most 20,000 instances of one generic type or method (more than five times the 3,492 of `Func<T1, T2, TResult>` in that app), and at most 500,000 instances in all (more than three times the 134,509 that app follows). The bounds keep such code from running the generation out of time and memory, and only such code reaches them, but they don't make it cheap. A polymorphic recursion such as `Go<A, B>` calling itself over three new pairs of its arguments (as in the unit tests) takes about 8 seconds and 690 MB, against minutes and gigabytes without the bounds. One that calls `Go<(A, X), B>` and `Go<A, (B, X)>` for three types `X` makes millions of small instances: it reaches the bound of one method in about 2 seconds and 250 MB, or in about 9 seconds and 1.4 GB, with about 42,000 seeds, when the methods of the tuples it makes are followed too. The instances left out SHALL be reported with `UNOWASM011` (FR-11).

**FR-3**: The task SHALL write a seed assembly, `Uno.Wasm.AotWrapperSeeds`, with a target method per distinct signature, which the AOT compiler doesn't compile and which takes and returns references as `object` (the runtime passes them alike), and static seed methods whose calls to the targets, 16 per seed method, are on the fall-through path of a branch that is always taken, and an AOT profile that lists only the seed methods. The target SHALL add the seed assembly to the AOT inputs and its profile to `WasmAotProfilePath`, and SHALL restore `WasmAotProfilePath` after the AOT compilation, as other targets read it as a single file.

**FR-4**: The task SHALL write the expected wrapper names of the seeded signatures: for signatures with up to 8 parameters, the `gsharedvt_in_sig` name as the runtime mangles it; above 8 parameters, the `interp_in` name as the AOT compiler names it, once per distinct wrapper. A signature whose names can't be predicted SHALL still be seeded, and SHALL be logged as unchecked.

**FR-5**: When `WasmShellEnableAOTWrapperSeedingCheck` is `true` (the default), the `_UnoValidateAOTWrapperSeeds` target SHALL run `ValidateAOTWrapperSeedsTask_v0` after `_WasmAotCompileApp`, list the functions defined in the `aot-instances.dll.bc` AOT bitcode with `llvm-nm`, and fail the build with `UNOWASM006` for each expected wrapper that isn't present, up to 50, then once with the count of the others. An `interp_in` name that several distinct wrappers share SHALL count once per variant the AOT compiler suffixes with `_0`, `_1`, ... When `llvm-nm` can't start, fails, or runs longer than 5 minutes, the build SHALL fail with `UNOWASM007`, with its error output, as when the expected wrappers can't be read.

**FR-6**: The seed assembly SHALL reference the assemblies that define the seeded types rather than facades, write primitive types as element types, and be identical for identical inputs, in any order (a fixed PE timestamp, a module version ID hashed from its content, and the inputs read in the order of their file names, as the first method collected for a signature gives its seed its types), as SHALL the profile and the expected wrappers.

**FR-7**: The seeding SHALL NOT change which of the application's methods are compiled.

**FR-8**: The task SHALL log `UNOWASM010` for each method with a body of the AOT inputs (the runtime enters the implementation of a method, whose parameters have their own flags, not an abstract declaration), whatever its number of parameters, one of whose parameters is a function pointer or a value type that the runtime doesn't map to a `Mono.ValueTuple` (not a generic one), passed by value, with Param flags (a default value, `[Optional]`, `[In]`, `[Out]` or `MarshalAs`). A parameter whose type is a generic parameter SHALL count with the type arguments of the instances that the task follows (FR-2): `inflate_generic_type` in `class.c` gives the type argument the flags of the parameter. The warning SHALL name the method with its parameter types, and the parameter by its position, with its name when the assembly has one (trimmed assemblies don't). It SHALL name the type of the parameter and what gives it its flags (a default value, or which attributes), say why such a type is affected when others aren't, and say that compiled code that calls the method can crash the app when it makes the call, or, above 8 parameters, when it starts running; above 8 parameters, for a virtual instance method, which the IMT slots of interfaces can hold, it SHALL say that compiled code that calls another method of its class through an interface can crash it too (static and non-virtual methods are never in an IMT slot). The flags of a return value SHALL NOT count: the wrapper caches key on `mono_signature_hash` in `metadata.c`, which hashes the parameters' flags through `mono_type_hash`, and the return type only by its element type, so a signature that only differs by the flags of its return value gets the same wrapper (the fifth review's `[return: MarshalAs]` variants of the test app, with 1 and 9 parameters, run from compiled code). When the layout of a parameter's type can't be told (a field type doesn't resolve), the task SHALL log the method at normal importance instead; when it's cyclic, or reaches a generic struct with 16 type arguments or more, the method SHALL count for the warning of that struct (below). The warning SHALL NOT advise listing the method in the AOT profile, and SHALL say that `NoWarn` removes it: compiling the method only moves the crash to interpreted code that calls it, as the runtime can't find the method's AOT-compiled `gsharedvt_out_sig` wrapper either, for the same reason as below, and `init_jit_call_info` in `interp.c` aborts. Measured on .NET 10.0.12 with the test app's 9-parameter `AttributedParameters.Describe`, whose parameter 9 is an explicit-layout struct with a default value: called from compiled code, it aborts at `interp.c:3420` when the profile doesn't list it, and runs when it does; called from interpreted code when the profile lists it, it aborts at `interp.c:2737`. An 8-parameter variant with the same parameter does the same from interpreted code, and from compiled code, when the profile doesn't list it, stops the app with "function signature mismatch"; without the default value, it runs. The large app has no such method, with any number of parameters, and neither have the 172 assemblies of the .NET 10.0.12 browser-wasm runtime pack, untrimmed. The task SHALL also log `UNOWASM010` once for each struct at the root of a cyclic layout, and once for each generic struct with 16 type arguments or more (FR-2), naming a method whose seed was left out for it, or else a method that this check found it in, and saying which of the two it is: compiled code can't enter the methods that take or return it, or a struct that holds it, by value. That warning SHALL NOT advise recording the profile either: compiled calls to such methods that can enter the interpreter make the AOT compiler overflow its stack or abort (`calls.c` adds their signatures to the interpreter entry signatures to compile, for every call outside the assembly, and for calls to methods the profile doesn't list). The runtime can't find the AOT-compiled interpreter entry wrapper of such a method, whatever the seeding does: `mono_metadata_parse_method_signature_full` in `metadata.c` gives the parameter types the flags of their Param rows; `get_wrapper_shared_type_full` in `mini-generic-sharing.c` returns those types as they are, flags included; the wrapper caches of `mini_get_interp_in_wrapper`, `mini_get_gsharedvt_in_sig_wrapper` and `mini_get_gsharedvt_out_sig_wrapper` hash the parameters' flags (`mono_signature_hash` and `mono_type_hash` in `metadata.c`); the AOT compiler doesn't encode them (`encode_type` in `aot-compiler.c`); and `find_aot_method_in_amodule` in `aot-runtime.c` only accepts the very wrapper the runtime asked for. Above 8 parameters, `interp_create_method_pointer_llvmonly` in `interp.c` then aborts, whenever the runtime resolves the method: when it builds an IMT slot the method is in, and when compiled code that calls it directly first runs, even if the call never happens (`init_method` in `aot-runtime.c` resolves the method's `MONO_PATCH_INFO_METHOD_FTNDESC` patches then; virtual call sites resolve their slot when they're called). With 8 parameters or fewer, the runtime gets `no_gsharedvt_in_wrapper` instead (`compile_special` in `mini-runtime.c`), and the call fails when it's made. Generic value types and parameters passed by reference are re-created without the flags, and aren't affected.

**FR-9**: Publishing again SHALL NOT compile the AOT inputs again because of the seeding (see "Republishing").

**FR-10**: An input or module that can't be read, a type, method, method instance or seed that can't be read or written (for example metadata the reader can't handle), a method or type that the check of FR-8 can't read, and a seed whose wrapper names can't be predicted (for example, because a field type doesn't resolve) SHALL only skip itself, or only go unchecked, logged at normal importance, once (the instances of a generic method whose body can't be read are reported with it), as SHALL references that fail to resolve because of malformed or unusual metadata. When writing the seed assembly fails, each seed SHALL be written alone, and those that can't be SHALL be left out. When the seeds can't be generated at all (for example, without `System.Private.CoreLib` among the AOT inputs), the task SHALL log `UNOWASM008` and delete the files of an earlier run, the target SHALL delete the stamp, so that it doesn't apply the seeding of the earlier run, and the build SHALL continue without the seeding and the check. When the SDK doesn't run the seeding in a profile-guided AOT publish, which happens if it renames the targets or properties the seeding hooks (see "Maintenance"), the build SHALL log `UNOWASM008` after `WasmNestedPublishApp`. A canceled build SHALL stop the generation before it writes any file.

**FR-11**: The task SHALL log `UNOWASM011` once for each cause of the bounds of FR-2: for instances whose generic arguments hold too many types, naming the method or type whose code or signatures use them, so that recursive code that makes ever larger instances, or a large instance with its methods and arguments, gives one warning; for the bound on one generic type or method, naming it; and for the bound on all instances, naming the generic type or method with the most instances. The warning SHALL suggest recording the AOT profile while that code runs, say where to report it, and that `NoWarn` removes it.

## Republishing

The SDK's AOT compiler compiles all the assemblies again when one of its inputs is newer than its output, and it copies the inputs into its `aot-in` folder only when their content changes. The seeding keeps a publish without changes from compiling anything:

- the generator writes the seed assembly, the profile and the expected wrappers only when their content changes, and identical inputs give identical files (FR-6);
- `_UnoGenerateAOTWrapperSeedsCore` has the AOT inputs, the task assembly and the targets file as inputs and the stamp as output, so a publish without changes skips the generation too. The task assembly's path is resolved against the targets file's folder, as `UsingTask` resolves it: for package consumers, `WasmShellTasksPath` is relative to it (`../tools`), while the inputs of a target resolve against the project, where the assembly doesn't exist, which would make the generation run on every publish. The package build replaces the version marker in the stamp's name with the bootstrapper's commit, so a version that hasn't generated in this folder since the inputs last changed generates again, even if its files are older than the stamp. A version that did keeps its stamp: switching back to it without changing the inputs reuses the files that the later version wrote, which are seeds for the same inputs, and which its check verifies. The stamp is deleted when one of the files is gone or the generation fails, and only touched when it succeeds;
- The AOT compiler compiles again only when one of its inputs is newer than its outputs (`CheckAllUpToDate` in `MonoAOTCompiler`), so dropping the seed assembly from its inputs, when the seeding doesn't apply after it did (the generation failed, or the seeding or deduplication was turned off), doesn't make anything stale: it would keep the deduplicated instances it compiled with the seeds. `_UnoValidateAOTWrapperSeeds` records the bitcode of the deduplicated instances (`aot-instances.dll.bc`) when the seeding applies, and `_UnoForgetAOTWrapperSeeds` deletes it, and the record, when it doesn't, so that the AOT compiler compiles them again without the seeds.
- `_UnoGenerateAOTWrapperSeeds` applies the seeding when the stamp exists. A publish doesn't add its file writes to the build's list, which `Clean` deletes, so `_UnoCleanAOTWrapperSeeding` removes the folder on `Clean`.

The check runs on every publish. Messages of the generation, such as `UNOWASM010` and `UNOWASM011`, are only logged when it runs, which the user documentation says.

Measured on the test app: a publish without changes takes about 10 to 20 seconds, depending on the machine's load, and the AOT compiler reports "Everything is up-to-date, nothing to precompile"; after touching a source file, the generation runs again, writes nothing, and the AOT step is skipped too (13 seconds).

## Maintenance

`WrapperSignature` reproduces how the runtime of .NET 10.0.12 normalizes and names the wrappers (dotnet/runtime at tag `v10.0.12`: `mini-generic-sharing.c`, `aot-compiler.c`, `debug-helpers.c`, `class-init.c`); in 9.0.11, the functions are equivalent for these rules (some differ in accessors and size checks). In .NET 11 RC2 (`v11.0.0-rc.2.26504.105`), they're unchanged and the abort is still at `interp.c:3420`, but `mono_class_layout_fields` adds extended layouts (`[ExtendedLayout]` C structs and unions), which keep their own type in the wrapper names, like explicit layouts, as `get_wrapper_shared_vtype` only maps auto and sequential layouts. `get_wrapper_shared_type_full` and `get_wrapper_shared_vtype`, whose mapping FR-2's struct checks follow, are the same in 10.0.13, 10.0.14, and 11.0 RC2 and RC3, and 9.0.11 has the same assertion against 16 type arguments. Mono on WebAssembly gets servicing fixes only, so these rules are only expected to change through servicing, if at all. The unit tests hold names that the AOT compiler of 10.0.12 emitted, and the test app's build compares the expected names with a real AOT compilation, so a runtime that names or normalizes the wrappers differently fails the check with `UNOWASM006` in CI. When a runtime update does:

1. Publish the test app (`src/Uno.Wasm.Tests.AOTWrapperSeeding`) and compare the names `UNOWASM006` reports with those `llvm-nm --defined-only obj/Release/<target framework>/wasm/for-publish/aot-instances.dll.bc` lists.
2. Find the change in the runtime functions above, mirror it in `WrapperSignature` (and `PrimitiveTypes` or `TypeNames`), and update the expected names of the unit tests and the version in `WrapperSignature`'s documentation.
3. Until a release has the fix, apps can set `WasmShellEnableAOTWrapperSeedingCheck` to `false`: the seeding still applies.

The seeding also relies on names of the SDK's build that aren't public, as the bootstrapper already did (`_SetupEmscripten` and `_WasmPInvokeModules`, for example). If an SDK renames one, the build shows it as follows, which fails the test script in CI:

| Name | Use | If an SDK renames it |
|------|-----|----------------------|
| `_WasmAotCompileApp` | The seeding runs before it, the check after it | The seeding doesn't run: `UNOWASM008` after `WasmNestedPublishApp` (FR-10) |
| `_WasmShouldAOT` | Whether the SDK AOT-compiles the build | The same |
| `_WasmAssembliesInternal` | The AOT inputs, which the seed assembly is added to | `UNOWASM008`: `System.Private.CoreLib` isn't among the AOT inputs |
| `_BitcodeFile` | The bitcode the check reads, which `_UnoForgetAOTWrapperSeeds` deletes when the seeding stops applying | `UNOWASM007`: the AOT compilation didn't write `aot-instances.dll.bc` |
| `WasmNestedPublishApp` (public, but not documented) | The check that the seeding ran, after it | That check doesn't run, and nothing reports it, but the test script still fails: no check line, and the unseeded app aborts |

The check that the seeding ran only covers publishes: a build that AOT-compiles (`RunAOTCompilationAfterBuild`) doesn't run `WasmNestedPublishApp`. The check finds `llvm-nm` through `EmscriptenUpstreamBinPath`, which the bootstrapper sets itself.

The seeding works around a runtime limitation: the AOT compiler only emits interpreter entry wrappers for the signatures of compiled call sites, while the runtime needs them for every method of an IMT slot. Mono on WebAssembly gets servicing fixes only: .NET 11 has experimental CoreCLR WebAssembly support, and CoreCLR becomes the standard in .NET 12 ([dotnet/runtime#134337](https://github.com/dotnet/runtime/issues/134337)). The workaround stays for Mono-based .NET 10 and 11 apps, and nothing is filed upstream.

## Non-Goals

- Signatures that only exist at run time: generic instances created through reflection (`MakeGenericType`), the code of the constructors with parameters that reflection runs (as dependency injection containers do), and delegates created with `Delegate.CreateDelegate`. For classes created through reflection, the interface instances that call sites name are covered.
- The code of generic classes and structs, and of the classes and structs nested in them (which have the generic parameters of the outer type in metadata), that implements generic methods (overrides of generic virtual methods, implementations of generic interface methods and of generic static abstract members), whether code calls them or creates delegates to them: their instances' signatures are seeded (FR-2), but the generic instances their bodies construct are only collected where other code names them. Pairing each instance of such a type with every call to a method of the same name multiplied the instances of LINQ's iterators in a large app until the bounds stopped them: its generation allocated 2.8 times as much, and logged six `UNOWASM011` warnings.
- Builds without an AOT profile (full AOT compiles every method) and builds that don't AOT-compile.
- CoreCLR on WebAssembly (experimental in .NET 11, the default in .NET 12). With `UseMonoRuntime` set to `false`, the SDK doesn't import the Mono targets (`WasmApp.Common.targets`), so `_WasmAotCompileApp`, which the seeding runs before and the check after, doesn't exist and `_WasmShouldAOT` isn't `true`; `_UnoGenerateAOTWrapperSeeds` also requires `UseMonoRuntime` not to be `false` (FR-1), so nothing of the seeding runs. Checked against the SDK targets of dotnet/runtime's main branch (`Microsoft.NET.Runtime.WebAssembly.Sdk/Sdk/Sdk.targets`, `BrowserWasmApp.CoreCLR.targets`); the .NET 11 WebAssembly workloads weren't installed where this was checked.
- Making the methods of FR-8 work, which takes a runtime fix.

## Edge Cases

- The application's profile may have been filtered by `WasmShellAOTProfileExcludedMethods` or `MonoRuntimeMixedModeExcludedAssembly`; the seed profile is appended to the filtered one.
- The wrapper names depend on runtime internals (see "Maintenance"). A runtime that names or normalizes them differently fails the check, which `WasmShellEnableAOTWrapperSeedingCheck=false` turns off while the seeding still applies.
- The AOT compiler escapes the bytes of non-ASCII type names with `isalnum` after `setlocale (LC_ALL, "")` (`mono_main` in `driver.c`, `append_mangled_type` in `aot-compiler.c`). On a build machine with a single-byte or double-byte locale, where bytes from 0x80 can count as alphanumeric, it can keep bytes the check expects escaped, and the check fails with `UNOWASM006` for signatures with such types. The check works in UTF-8 and C locales, which CI and most build machines use.
- `interp_in` names hold only the parameter types, so wrappers that differ only in their return type or in having `this` share a name; another wrapper of the same name can stand in for a missing one in the check.
- Wrapper names don't hold assemblies either, so same-named value types of different assemblies get distinct wrappers of the same name: the check counts such `interp_in` wrappers once per variant (FR-5), and looks for such a `gsharedvt_in_sig` name once. Function pointers of any signature have the same name, `*()`, and are counted the same way.
- Seeds don't keep custom modifiers, which the runtime keeps in the wrapper signatures of function pointers (the calling convention modifiers of `delegate* unmanaged[SuppressGCTransition]<...>`, for example) and of `void` returns (`modreq(IsExternalInit)` of `init` accessors): `get_wrapper_shared_type_full` returns those types as they are, and the wrapper caches compare custom modifiers. The seeded wrapper of such a signature isn't the one the runtime looks for, and the check can't tell, as the names leave the modifiers out (`append_mangled_type` in `aot-compiler.c`). In deduplication mode, the AOT compiler also names `gsharedvt_in_sig` wrappers by these names, so keeping the modifiers couldn't be checked without a run-time test. It only matters above 8 parameters or for `gsharedvt` callers, so it's left as a limitation.
- With up to 8 parameters, the methods of FR-8 get a `gsharedvt_in_sig` stub that fails when called, so they only crash when compiled code calls them while they're interpreted, rather than as soon as the code that calls them runs; the task warns about them all the same.
- When the AOT compiler can't compile a seed method (for example, because a type of one of its signatures fails to load), the up to 16 signatures it seeds lose their wrappers, and the check reports them.
- The app's own compiled code that calls a method with a value type whose layout is cyclic makes the AOT compiler overflow its stack, and with a generic struct of 16 type arguments or more makes it abort, as does compiling a method that takes or returns one, whatever the seeding does; the seeding only leaves its own seeds of such types out (FR-2).
- The implementations of generic virtual methods are paired with the calls by name (FR-2), so an implementation whose name differs from the method it implements, which VB's `Implements` or an IL `.override` can give, isn't followed; C# keeps the name, or prefixes it with the interface's.
- Mono.Cecil 0.11 throws on a MethodImpl row whose body is a member reference when it reads a method's overrides, which C# compilers don't emit (they emit forwarding methods instead), and may then keep a partial map for the other methods of the module. The throw only skips the method being scanned (FR-10); a partial map can only leave out the static abstract implementations of that module.
- The layout cache (FR-2) gives each walk bound where walking again would, but when a cached walk would cross both, the depth bound fires first, which walking again might not do: that needs more than 100,000 steps more than 64 value types deep, which no real struct has.
- `llvm-nm` exiting with an error, failing to start, or running longer than 5 minutes fails the build with `UNOWASM007` (FR-5).
- With `WasmShellEnableAOTDeduplication` or `WasmDedup` set to `false`, the build logs `UNOWASM009` and continues without the seeding and the check; `WasmShellEnableAOTWrapperSeeding=false` removes the warning.
- If the seeds can't be generated, or the SDK doesn't run the seeding, the task logs `UNOWASM008` and the build continues without the seeding and the check (FR-10).
